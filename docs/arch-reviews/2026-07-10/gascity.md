# gascity — Architecture Review

_Repo: `/home/ds/gascity-main` (module `github.com/gastownhall/gascity`) · Go 1.26 · 2,564 `.go` files · ~419K non-test LOC · 151 packages · reviewed 2026-07-10 · read-only._

## Executive summary

Gas City is a multi-agent orchestrator with a genuinely good intended architecture: a documented layered model (`engdocs/architecture/invariants.md`) where a canonical object model in `internal/*` is the center and the CLI and HTTP+SSE API are two thin "projections" over it. The domain packages themselves are mostly cohesive, dependency inversion around `internal/runtime` (the provider contract) is clean, the event **payload** layer is typed and generated from a single registry, and the open-core boundary is guarded by real CI checks. The problem is **drift between that intended architecture and the actual one, concentrated in two god-objects.** `cmd/gc` is a single flat `package main` of 309 non-test files / ~144K LOC that holds the supervisor/reconciler brain, desired-state computation, and session-lifecycle orchestration — business logic the invariants doc says must live in `internal/` — and it absorbs 54% of all commits. `internal/api` is a fat `*Server` with no service layer whose 138 handlers reach directly into 51 domain packages (repo-max fan-out) and hand-maintain CLI↔API parity. Secondary drift: `internal/config` carries routing/pool business rules and upward deps (its own doc says otherwise), "dispatch" names three different things, and the event-**type** identifier is a bare string copied across four representations held in sync by drift tests. None of this is a rewrite; the leverage is in extracting the reconciler/domain out of `cmd/gc` into `internal/` and interposing a shared operations layer that both projections call.

## Ranked findings (by ROI = reach ÷ effort, discounted by risk)

---

### 1. `cmd/gc` is a 144K-LOC god `package main` holding the supervisor's brain — the "CLI is a thin projection" invariant is violated

- **Evidence:**
  - `cmd/gc` = 309 non-test `.go` files, ~144,558 LOC, one flat `package main`. **All 731/731 files declare `package main`, so nothing here is importable by any other package.** It absorbs **2,541 of 4,733 commits since Jan (54%)** — the dominant churn surface in the repo.
  - Split by convention: 89 `cmd_*.go` files = 60,794 LOC (cobra wiring, but many embed real dispatch/lifecycle logic inline, e.g. `cmd_nudge.go` 2,542, `cmd_sling.go` 2,003, `cmd_order.go` 1,904); the other 220 files = 83,764 LOC and are almost entirely domain logic. **~60–70% of the package (~90K+ LOC) is logic that conventionally belongs under `internal/`.**
  - The supervisor/controller reconciliation loop lives in `package main`, not in `internal/supervisor`: `session_reconciler.go` (5,530, doc-comment "implements the bead-driven reconciliation loop"), `build_desired_state.go` (4,553), `session_lifecycle_parallel.go` (3,248), `order_dispatch.go` (3,150), `controller.go` (1,427), plus `compute_awake_set.go`, `reconcile_tick.go`, `session_reconcile.go`. The reconciler cluster alone ≈ **16,305 LOC**, versus `internal/supervisor` at just **2,173 LOC** (config, maintenance, registry, restartcause). Session domain is 35 `session_*.go` files = **23,309 LOC** in main, mirroring the extracted `internal/session` (29K). Also in main: 34 `dolt_*.go`, 13 `doctor_*.go` (parallel to the extracted `internal/doctor`), a full reaper/GC set, and `bead_policy_store.go` (a `beads.Store` decorator).
  - `engdocs/architecture/invariants.md:24` states the normative rule: _"The object model is the center… All business logic lives there [`internal/*`]. The two surfaces below call into it; neither re-implements validation, routing, or invariants."_ The reconciler/desired-state logic has no `internal/` home to call.
  - **This drift is documented and the extraction is explicitly in progress, not accidental:** `engdocs/design/session-lifecycle-domain-cleanup-plan.md` (Status: "Implemented with boundary hardening") is a live plan to hoist lifecycle logic out of "reconciler repair paths, manager helpers, and API/CLI writers" into a single `internal/session` boundary. **53 cmd/gc files are already thin type-alias/delegation shims** to extracted packages (e.g. `cmd/gc/convoy_fields.go` is a 21-line `type ConvoyFields = convoy.ConvoyFields` shim over the real 78-line `internal/convoy` impl) — an "extract, leave an alias" migration that has only partially landed.
- **Why it matters (leverage):** This one package is where >half of all future changes land and where the worst merge/review pressure concentrates. Because domain logic sits in `package main`, `internal/api` **cannot import it** and must reach it through hand-threaded interfaces implemented in `cmd/gc/api_state.go` (`controllerState implements api.State, api.StateMutator`), wired at `controller.go:1362` — i.e. finding #2's fat adapter exists _because_ of this finding. Continuing the documented extraction (reconciler + desired-state + session-lifecycle → `internal/supervisor`/`internal/session`) gives every controller change a testable, importable home, and lets both projections call the same ops directly instead of via runtime-threaded interfaces. It removes a concept ("business logic that happens to live in main") rather than adding one.
- **Effort:** L (mechanical but large: move ~30–40 files cluster-by-cluster). The migration is already partly done (53 shims prove the pattern works), so this is continuation, not a new initiative. Extract one cohesive cluster at a time (reconciler → desired-state → session lifecycle).
- **Risk:** Medium, and lower than a cold start because a maintainer-owned plan and 53 landed shims already exist. Pure code motion, no behavior change; blast radius contained by the compiler and a large test corpus (422 `_test.go` in cmd/gc, 32 txtar scripts). Reversible per-cluster. Main hazard: unexported `package main` symbols that must become exported at the new boundary — surfaced immediately by the build.

### 2. `internal/api` has no service layer: 138 handlers on a fat `*Server` reach into 51 packages and hand-maintain CLI↔API parity

- **Evidence:**
  - `internal/api` non-test = ~40,474 LOC hand-written **plus** one generated client file `genclient/client_gen.go` at **41,950 LOC (51% of the package's line count)**.
  - **Highest fan-out in the repo: `internal/api` imports 51 internal packages.** There is no service/usecase layer — handlers are 138 methods on a single `*Server` whose only real field is `state State` (`server.go:52`), each reaching directly into `agent`, `beads`, `config`, `convoy`, `formula`, `mail`, `molecule`, `orderdispatch`, `orders`, `session`, `sling`, `supervisor`, `worker`, … and constructing domain objects inline (`sling.New`, `session.NewManagerWithOptions`, `worker.NewFactory`). The 51-edge fan-out is the mechanical consequence.
  - **Parity is maintained by hand, not by a shared operation.** For sling, the CLI enters the domain at `sling.DoSling`/`DoSlingBatch` (`cmd/gc/cmd_sling.go:826`), while the API re-implements the intent switch (`direct`/`attached`/`standalone`) over the lower-level `sl.RouteBead`/`LaunchFormula`/`AttachFormula` (`internal/api/handler_sling.go`) with ~60 lines of inline validation (`huma_handlers_sling.go:34-93`). The recent commit _"feat(sling): dashboard deep link … CLI + JSON + API parity"_ exists precisely because the deep-link discrimination is copied: CLI checks `WorkflowID != "" && len(Children)==0 && ContainerType==""` (`cmd/gc/sling_dashboard_link.go:73`) vs API relying on `WorkflowID` alone (`huma_handlers_sling.go:159`) — condition drift is a live risk.
  - **Two coexisting handler generations:** 30 legacy `handler_*.go` files (registered on a per-city `ServeMux`, `server.go:281/307`, kept "for tests") vs 22 production `huma_handlers_*.go`. The legacy files double as shared-helper homes (`enrichSessionResponse`, `execSling`), so they are a compatibility shim, not dead code — but the dual surface is a standing tax.
- **Why it matters (leverage):** A thin operations/usecase layer (e.g. `internal/ops` or methods on the domain packages) that both `cmd/gc` and `internal/api` call would (a) collapse the 51-package fan-out to a handful of service imports, (b) make CLI↔API parity structural rather than a per-feature hand-sync, and (c) delete the class of bugs the "parity" commits keep fixing. This is the natural sink for the logic extracted in finding #1 — do #1 and #2 together and the shared layer is where both projections meet.
- **Effort:** M–L (introduce the layer incrementally, starting with the operations that already have parity pain: sling, session-create, title-generate). Not a rewrite — most cores already exist in `internal/sling`, `internal/session`, `internal/worker`; this hoists the intent/validation/assembly glue up into one shared place.
- **Risk:** Medium. Reversible; each operation migrated independently behind unchanged wire/CLI surfaces, guarded by the OpenAPI drift test and txtar CLI tests.

### 3. `internal/config` holds routing/pool business rules and has upward dependencies its own doc denies

- **Evidence:**
  - `config.go` is 4,377 lines; the package carries **115 `Effective*`/business-rule methods** (`grep 'func.*Effective'`) including `EffectiveSlingQuery`, `EffectiveWorkQuery`, `EffectivePoolDemandQuery`, `EffectiveScaleCheck`, and `bdReadyPoolDemandShell()` — the shared shell-predicate substrate the reconciler (spawn side) and worker (claim side) both derive from. `engdocs/architecture/dispatch.md:253-277` elevates this to a normative invariant, so the **routing/pool-demand policy lives in the config package**, not in a dispatch/domain package.
  - config imports **12 internal packages**, including two upward/conceptual-inversion deps: `internal/orders` (`config.go:4053`, `webhook.go:571`, `pack.go:1535`) and `internal/agent` (`named_sessions.go:118`). No import cycle exists (verified — orders/agent don't import config back), so it compiles, but it contradicts the layering.
  - The package's own doc `docs/reference/… config.md:71-74` asserts _"It has no upward dependencies… config depends only on `internal/fsys`… and BurntSushi/toml."_ That is false against the code — a documented-vs-actual drift.
- **Why it matters (leverage):** config has fan-in 25 (nearly every package imports it), so its conceptual weight is paid everywhere. Splitting the pure config **types/loading** (the real Layer-0 primitive) from the **routing/pool policy** (a derived mechanism that belongs beside dispatch/sling) clarifies the single most-imported package in the tree and makes the "config is a leaf primitive" invariant true again. Medium reach, low-ish effort.
- **Effort:** M. Move the `Effective*` routing/pool methods into a `policy`/`dispatch`-adjacent package that depends on config, not vice versa; drop the `orders`/`agent` back-references (likely small helper relocations).
- **Risk:** Medium. Fan-in 25 means wide recompilation, but mechanical; the shared-predicate invariant has a dispatch test guarding it (`dispatch.md` correspondence), so a regression is caught. Update the stale doc in the same change.

### 4. "Dispatch" names three different things — stale doc + package-name collision

- **Evidence:** `engdocs/architecture/dispatch.md:64` (verified 2026-05-21) says _"Dispatch is not a separate Go package. It is a composition of primitives orchestrated by `cmd/gc/cmd_sling.go`."_ Reality: (1) the sling logic **was extracted into `internal/sling`** (3,719 LOC; `cmd_sling.go` is now thin aliases, `type slingOpts = sling.SlingOpts`); (2) a **separate `internal/dispatch`** package (7,706 LOC) is the _control dispatcher_ — `ProcessControl`, retry/ralph loops, `ReconcileClosedScopeMember` (`control.go:144`) — an unrelated concern (formula-graph execution). The architecture doc named "Dispatch (Sling)" mentions neither package.
- **Why it matters:** The one word "dispatch" forces every reader to disambiguate sling-routing vs control-bead-execution, and the canonical doc actively misleads (says the package doesn't exist). This is a cheap correctness fix to the shared mental model that pays off on every dispatch/sling change and every onboarding.
- **Effort:** S. Update `dispatch.md` to name both `internal/sling` and `internal/dispatch`; optionally rename `internal/dispatch` → `internal/controlgraph` (or similar) to kill the collision.
- **Risk:** Low (doc-only) to Medium (if renaming the package — mechanical, compiler-checked, reversible).

### 5. Event **type** identity is a bare string duplicated across four representations, reconciled by drift tests

- **Evidence:** Event types are 75 untyped `string` constants in `internal/events/events.go` (no `EventType` type; `Event.Type string` + opaque `Payload json.RawMessage`). The same wire strings are re-declared in ≥4 places: (1) canonical Go constants; (2) `pkg/eventexport` keeps its own **raw literal allowlist** and deliberately does not import `internal/events` (kept in lockstep only by `internal/eventfeed/allowlist_drift_test.go`); (3) hand-written dashboard **TypeScript literals** (`internal/api/dashboardspa/web/frontend/src/attention/registry.ts`, `beadsNeedingAttention.ts`, `entityLinks.ts`); (4) generated TS/Go client types. The **payload** layer is well-designed (sealed `Payload` interface + string-keyed registry + OpenAPI union generated by reflection) — only the **type identifier** string is the fragile, replicated axis, and it undercuts the "typed wire end-to-end" invariant (`invariants.md`).
- **Why it matters:** Adding or renaming an event today means touching Go constants, the eventexport allowlist, and hand-written dashboard TS, with only tests as the guardrail. Modest reach (event surface), but the fix removes a whole hand-sync ritual.
- **Effort:** M. Make the event-type an exported enum and generate the eventexport allowlist and the dashboard TS union from the single Go source (the payload registry already proves the generation pattern works).
- **Risk:** Low–Medium. Additive generation; drift tests already exist to prove equivalence during migration; the `pkg/eventexport` no-`internal`-import boundary must be preserved (generation writes literals, not an import).

## Leave unchanged (scoped, not overlooked)

- **`internal/runtime` provider contract.** Fan-in 24 is misleading — 16 of its importers are its own provider sub-packages (`tmux`, `subprocess`, `k8s`, `ssh`, `acp`, `herdr`, …) depending on the `Provider` interface they implement. This is textbook dependency inversion; the 13 capability interfaces are accreting slightly but the package is cohesive. Protect it.
- **Event payload layer** (`internal/events` sealed-interface registry → generated OpenAPI union). Single source of truth, self-registering, CI-guarded. Good as-is (the type-string axis in finding #5 is the only weak spot).
- **Open-core boundary enforcement** (`scripts/check-core-boundary.sh`, `check-eventexport-isolation.sh`). Fails-closed structural guards for commercial/tenancy leakage and the `pkg/eventexport` no-`internal` boundary. Exemplary; keep.
- **`internal/beads` store abstraction.** Multiple backends (file/mem/native-dolt/caching/lib) behind a conformance-tested `Store` contract (`*_conformance_test.go`). Cohesive and well-guarded.
- **Code-first OpenAPI generation** (Huma types → spec → `genclient`, drift-tested). The generated 42K-line client is not a problem — it is generated and diffed in CI. The API problem is the missing service layer (finding #2), not the codegen.
