# codeprobe — Architecture Review

_Read-only architectural review, 2026-07-10. Scope: `src/codeprobe/` (225 modules, ~61.5K LOC). Focus: structure, boundaries, dependency graph, coupling/cohesion, drift — not style or line-bugs._

## Executive summary

codeprobe is a well-conceived **assess → mine → run → score → interpret** pipeline with a genuinely clean design intent (adapter/collector Protocols, ZFC discipline, a LikeC4 model kept in sync with source). The domain packages exist and the dependency direction is mostly right: `mining`/`core`/`analysis` sit below `cli`, and no package imports upward into `cli`. The strengths worth protecting: the three-Protocol adapter boundary, the single judge-LLM function with swappable backends, the scorer-honesty lint gate, and the architecture-as-code model.

The structural debt concentrates in three recurring signatures. First, **layer inversion masked by lazy imports**: `core` imports policy constants *upward* from `analysis`, and `core/__init__` eagerly pulls the whole executor→scoring→analysis graph, forcing ~6 deferred in-function imports to hide the fact that `core`/`analysis`/`models` are not a DAG. Second, **orchestration smeared into the CLI**: `mine_cmd.py` (3,498 lines) and `run_cmd.py` (`run_eval`, 666 lines) hold pipeline routing and an experiment loop that the in-process `api.py` cannot reach and re-implements in parallel. Third, **a general error taxonomy trapped under `cli/`**, forcing four domain modules into lazy imports and two duplicate forks.

The highest-ROI moves are cheap and low-risk: relocate the error taxonomy and the reward-classification policy to leaf packages (breaks the cycle and the forks), and unify the two experiment-execution paths behind one `core`-level orchestrator. The expensive items (decomposing `executor.py` and `mine_cmd.py`) are real but should follow the cheap structural fixes, not precede them.

## Ranked findings (by leverage ÷ effort, discounted by risk)

### 1. Error taxonomy `cli/errors.py` is misplaced under the CLI package — NEW
- **Evidence:** `cli/errors.py:3-15` deliberately does *not* subclass `click.ClickException`; it defines plain serializable `@dataclass` errors (`CodeprobeError`/`PrescriptiveError`/`DiagnosticError`) with nothing CLI-specific. Yet four domain modules must import it *across the CLI boundary and lazily*, each with a comment that a module-load import would drag in the Click layer: `net/offline.py:81-84`, `adapters/models.py:135-137`, `tenant_lock.py:93-96`, `tenant.py:57`. Two packages gave up and fork the classes: `config/defaults.py:64-98` and `tenant.py:68-80` (`_FallbackDiagnosticError` + `_lazy_diagnostic_error()`).
- **Why it matters (leverage):** the taxonomy is a cross-cutting domain concern miscategorized as a CLI concern, producing an inverted dependency (domain → cli), load-order-fragile lazy imports, and two forks that can silently drift from the canonical three classes. Moving it to a leaf `codeprobe/errors.py` lets `cli`, `core`, `net`, `adapters`, `tenant`, `config` all import at module scope and deletes both forks.
- **Effort:** S · **Risk:** Low, mechanical, fully reversible (module move + import rewrites + delete two forks; `cli/errors.py` can re-export for back-compat).

### 2. Reward-classification policy lives in `analysis`, inverting the core↔analysis layer — NEW
- **Evidence:** `analysis/stats.py:23` defines `PASS_THRESHOLD` and the run-classification predicates `is_quota_casualty`/`is_scorable_run`/`partition_reward_population` (`stats.py:63-125`). `core` then imports these *upward*: `core/scoring/{result.py:17, ir.py:13, scorers.py:19}` import `PASS_THRESHOLD`; `core/experiment.py:12` imports `is_quota_casualty, is_scorable_run`. The back-edge (`analysis.stats` needing `core.tool_surface_audit`) is closed only by deferred imports at `stats.py:442-447, 549` with a comment admitting the cycle; `analysis/dual.py:11-12,90` does the same. `core/scoring/__init__.py:25` re-exports the threshold it imported *from analysis*, even though the threshold is a scoring constant.
- **Why it matters (leverage):** `stats.py` is two modules fused — pure statistics (`wilson_ci`, `mcnemars_exact_test`, `cliffs_delta`, dependency-free) plus reward/run-classification *policy* the scoring layer needs. Relocating the ~90 lines of policy + `PASS_THRESHOLD` down to a leaf (`core/scoring/result.py` or a new `models`-tier `reward_policy.py` depending only on `models.experiment`) flips the edge to point downward and turns every deferred import at `result.py:17`, `ir.py:13`, `scorers.py:19`, `experiment.py:12`, `stats.py:446/548` into a normal top-level import. Companion: `core/bias_detection.py:37` and `core/tool_surface_audit.py:34` import nothing but `models.experiment` — they are `models`-tier files misfiled under `core/`; moving them removes the last conceptual core↔analysis coupling and lets `core/__init__` and `analysis/__init__` import top-level.
- **Effort:** S-M · **Risk:** Low, contained to relocation + import rewrites; behavior unchanged, easily reverted.

### 3. Two parallel experiment-execution paths: `run_cmd.run_eval` vs `api.run_experiment` — NEW
- **Evidence:** `run_eval` (`run_cmd.py:417-1083`, a ~666-line function with a nested `_run_config`) and `run_experiment` (`api.py:90-230`) independently re-implement the same loop and share only the leaf primitive `core.executor.execute_config`. `run_cmd.py` does not import `api.run_experiment`. Both re-do: task discovery (two divergent impls: `api._discover_task_dirs` at `api.py:67-87` vs `run_cmd._find_tasks` at `run_cmd.py:184-200`), permission-mode validation, adapter resolution, layered model/timeout/max_turns resolution, `resolve_tool_policy`, `AgentConfig` build, `adapter.preflight`, `CheckpointStore.from_legacy_path`, and `generate_report`. They already diverge on one rule: `config_max_turns_source` is `"experiment"|""` in `api.py:164` but adds `"cli"` in `run_cmd.py:778-783`.
- **Why it matters (leverage):** every change to how a config resolves into an `AgentConfig` (new field, new precedence, new preflight step) must be made twice or the notebook/library path silently drifts from the CLI path. This is a correctness liability, not just duplication. A single `core`-level `run_config(exp_config, ...)` that both callers wrap collapses the fork and gives `api.py` the same execution semantics as the CLI.
- **Effort:** M · **Risk:** Medium — touches the hot execution path; mitigate with the existing experiment fixtures and by extracting behavior-preserving first, then deleting the fork.

### 4. `core/llm.py` and `llm/backends/` are two drifted LLM stacks, one largely unused — NEW
- **Evidence:** Two separate `LLMBackend` Protocols exist and reference neither: `core/llm.py:108` and `llm/backends/base.py:37`. Two model-alias tables must agree: `core/llm.py:63-78` (`_ANTHROPIC_MODELS`/`_OPENAI_MODELS`) and `llm/model_registry.yaml`; `core/llm.py:56-62` explicitly admits the invariant, policed only by a test. The registry stack (`llm/backends/{anthropic,bedrock,vertex,azure_openai,openai_compat}.py`) has consumers only at `cli/check_infra.py:332` and `snapshot/manifest.py:111`, and both call **only `get_registry()`** (name→id lookup) — the multi-vendor `complete()` implementations (bedrock/vertex/azure) appear to have no production caller. Meanwhile all actual judge/mining calls go through `core/llm.py`'s hand-rolled three-backend set.
- **Why it matters (leverage):** the subject-vs-judge split (adapters vs `core/llm.py`) is principled; the judge-vs-registry split is drift. Two backend Protocols and two model tables mean model/routing knowledge is maintained in two shapes with a test as the only guard. Either wire the judge path onto the registry (single source of model identity) or delete the unused `complete()` scaffolding — both shrink the concept count.
- **Effort:** M · **Risk:** Medium — need to confirm no external/library consumer of the registry `complete()` before deleting; the merge direction (adopt registry) is lower-risk than it looks since it is additive.

### 5. Adapter Protocol under-specifies the contract the executor actually depends on — NEW
- **Evidence:** `adapters/protocol.py:181-227` declares only `name`, `preflight`, `run`, `isolate_session(slot_id)`. The executor reaches three undeclared members by `getattr`/signature-sniffing: `set_trace_context(...)` (`executor.py:1184-1187`, not in the Protocol), `cleanup_session_namespace(namespace)` (`executor.py:234-237, 1499`, not in the Protocol), and `isolate_session` called with a `namespace=` kwarg the Protocol signature lacks — the executor introspects `inspect.signature` (`executor.py:217-226`) to decide whether to pass it, while `ClaudeAdapter.isolate_session(slot_id, namespace=None)` (`claude.py:467`) diverges from the declared signature.
- **Why it matters (leverage):** the real adapter interface is larger than `AgentAdapter` and enforced only by runtime duck-typing, so a `@runtime_checkable` Protocol gives false assurance and a new adapter author cannot see the true contract. Folding the three members into the Protocol (or a second `SessionAwareAdapter` Protocol) makes the contract type-checkable and deletes the signature-sniffing branch.
- **Effort:** S-M · **Risk:** Low — additive to the Protocol; the three concrete adapters already implement the members.

### 6. Task-directory format is not single-sourced; grader logic lives as string-literal Python — NEW
- **Evidence:** `mining/writer.py` (1,812 lines) mixes TOML manifest serialization (`write_suite_manifest:37`), **three full grader programs embedded as triple-quoted string literals** (F1/tiered file-list scorer at `writer.py:182`, text/oracle scorer at `355`, `py_compile` checkpoint at `757`), filesystem layout (`write_task_dir:1177` branching into oracle/dual/default inline at `1217/1231/1254`), validation, and instruction rendering. The literal task-contract filenames (`instruction.md`, `metadata.json`, `ground_truth.json`, `reward.txt`, `metrics.json`, …) appear across ~20 sites in `writer.py` **and** independently in `mining/comprehension_writer.py:117-146` — a second, forked task-dir writer.
- **Why it matters (leverage):** the grading contract (what `reward.txt`/`metrics.json` must contain) is executable Python encoded as strings — invisible to type-checkers, linters, and host-side tests — and the directory schema is duplicated between two writers, so a format change can silently diverge between comprehension tasks and everything else. A single `TaskDir` schema object (owning filenames + layout) and extracting the embedded graders to real, tested modules removes both hazards.
- **Effort:** M · **Risk:** Medium — the embedded scripts are the actual scoring behavior; extract with golden-output tests before moving.

### 7. `mine_cmd.py` (3,498 lines) is the mining orchestration engine, unreachable from `api` — NEW
- **Evidence:** Pipeline routing lives in the CLI: `_dispatch_by_task_type` (`mine_cmd.py:1394`) fans out to `_dispatch_cross_repo:1482`, `_dispatch_sdlc:1886`, `_dispatch_probes:2000`, `_dispatch_comprehension:2050`, `_dispatch_mixed:2220`, `_run_org_scale_mine:2837`. Also inline: the goal/preset/profile/flag precedence algorithm (`resolve_effective_config:1264-1386`), a profile-persistence config store (`load/save/list_profiles:1178-1263`), and dual-verification/suitability orchestration (`_apply_dual_verification:1618`, `run_mine:2402`). The six mining flows (`extractor.mine_tasks`, `multi_repo.mine_tasks_multi`, `org_scale.mine_org_scale_tasks`, `comprehension`, `dependency_upgrade`, refresh) share no `Pipeline`/`Stage` seam — each CLI dispatcher re-implements "call entry fn → post-process → write."
- **Why it matters (leverage):** the domain package `codeprobe.mining` exists, but the orchestration that sequences its primitives is locked in a 3,498-line Click file, so the in-process `api.py` cannot mine and any flow/contract change touches N entry functions + N dispatchers. Lifting precedence-resolution, profile persistence, and dispatch into `codeprobe.mining` (mirroring how `snapshot_cmd.py` cleanly delegates to `codeprobe.snapshot`) gives a reusable, testable mining API and thins the CLI to argument-binding.
- **Effort:** L · **Risk:** Medium — large surface; do it after findings 1-3 so the extracted code lands on a clean layer.

### 8. `core/executor.py` (1,540 lines) is a God-module with two parallel dispatch bodies — NEW
- **Evidence:** `execute_config` (`executor.py:1078`) mixes seven concerns in one function: thread-pool + a process-global semaphore (`145-160, 1465`), checkpoint restore/append (`1119, 1292`), cost-budget accumulation + 80% warning (`1319-1335`), OAuth-quota halt (`1266-1284, 1484`), event emission (`1154, 1299, 1518`), git workdir reset/HEAD-restore between tasks (`1393, 1411`), and sibling-experiment quarantine (`1364`). The sequential (`1365-1413`) and threaded (`1414-1501`) dispatch bodies each re-implement TaskStarted emission, halt checks, and crash-capture. `execute_task` (`445-885`, ~425 lines) folds metadata read, reward-type auto-detection, turn-cap resolution, worktree acquisition, preamble composition, commit pinning, multi-repo setup, materialize-eligibility, source quarantine, the adapter call, and three error-classification exits.
- **Why it matters (leverage):** this is the single most-churned file (68 commits/6mo, second overall) and the de-facto system core; every new execution concern accretes here. Splitting the cross-cutting policies (budget, quota-halt, checkpoint, event emission) out of the dispatch loop and unifying the sequential/threaded bodies behind one iterator removes the parallel-maintenance tax on the hottest path.
- **Effort:** L · **Risk:** Higher — hot concurrency path with quota/checkpoint semantics; requires the existing fixtures plus targeted concurrency tests, done incrementally.

### 9. Symbol-from-diff extraction is re-hand-rolled 3× and reference-finding 2× — NEW
- **Evidence:** "regex-match def/class lines in a git diff → modified symbols" exists three independent times with three regex dialects: `extractor.py:381/435` (`_SYMBOL_*`, `git show`), `multi_repo.py:812` (`_SYMBOL_EXTRACTORS`, `git show <sha>`), `org_scale_scanner.py:1147/1261` (`_DEF_IN_DIFF_PY`/`_DEF_IN_DIFF_GO`, `git log --diff-filter=M -p`). `multi_repo.py:36-39` already imports `get_changed_files`/`list_merged_prs` from `extractor` but re-rolls its own symbol extraction instead of reusing it. "Word-boundary reference finder" exists twice: `multi_repo.py:170 RipgrepResolver.find_references` (rg + python fallback) and `org_scale_scanner.py:431 find_callers_of_symbols`.
- **Why it matters (leverage):** the "what symbols did this commit touch" primitive is core to three mining flows, and three regex dialects can classify the same diff differently — a silent correctness divergence in the task corpus. A shared `git-diff-symbols` + `symbol-references` module gives one dialect and one fallback policy.
- **Effort:** M · **Risk:** Medium — behavior-consolidating change to mined output; guard with fixtures comparing the three dialects' outputs before merging.

### 10. Redundant per-task copy-isolation layered three deep; four unrelated "sandbox" concepts — NEW
- **Evidence:** Per task, three copy/isolation layers run: `WorktreeIsolation.acquire()` (`core/isolation.py:947`) hands the executor a worktree, then `_score_in_sandbox` does its own `shutil.copytree` (`executor.py:338-346`), then `_run_in_sandbox` does a *third* `copytree` (`core/scoring/sandbox.py:195`) — the last two are separate reimplementations of "isolate the task dir before scoring," each carrying duplicated `COPYTREE_IGNORE`/`_safe_env`/secret-sanitization. Separately, four modules share the "sandbox" word for different things: `core/isolation.py` (worktree pool), `core/scoring/sandbox.py` (scoring jail), `core/sandbox.py:36` (`is_sandboxed()` container detection), `cli/_sandbox.py` (a Click `--allow-mutating-tools` flag).
- **Why it matters (leverage):** the double scoring-side copytree is a redundant per-task filesystem cost with two copies of the ignore/redaction policy that can drift; consolidating to one owner removes a copy and a policy fork. The four-way name collision is a comprehension hazard — a reader cannot tell which "sandbox" a symbol denotes.
- **Effort:** M (copytree consolidation) / S (rename for disambiguation) · **Risk:** Medium — the copy layers carry secret-redaction; preserve redaction behavior under test.

### 11. LLM prompt/parse boilerplate duplicated across ~6 mining call sites — NEW
- **Evidence:** The "build prompt → `call_claude(LLMRequest(model="haiku", timeout_seconds=30, …))` → parse JSON" sequence is copy-pasted with its own `_build_*_prompt`/`_parse_*_response` at `curator_tiers.py:149/274/420`, `curator_backends.py:393/510`, `oracle_curator.py:363`, `dependency_upgrade.py:209`, `extractor.py:1497`, `org_scale.py:308/1456`. Model and timeout policy are hardcoded at every site. (The LLM *boundary* itself is clean — one `call_llm` with three swappable backends.)
- **Why it matters (leverage):** model/timeout/routing policy for mining enrichment is set in 6+ places rather than one, so a policy change (e.g. bump the judge model) is a scatter-edit. A thin `mining` LLM-task wrapper (prompt → typed parse) centralizes it. Lower priority: it is duplication, not a cycle or correctness trap.
- **Effort:** S-M · **Risk:** Low.

## Minor / doc drift (not ranked)

- **AGENTS.md references a moved module:** it points scorer authors at `core/scoring.py` (`AGENTS.md:51`), but that file was split into the `core/scoring/` package (commit `a8818eb`). Stale onboarding pointer.
- **Envelope plumbing hand-assembled per command:** `resolve_mode → branch → emit_envelope` is open-coded in ~14 command files (no decorator/context-manager captures the "resolve mode → run → emit success/error" contract), so commands can and do drift on which branches they emit. A single command decorator would standardize it. (Effort S-M; modest leverage — the helpers already exist, only the integration is repeated.)
- **`validate_cmd.py` (926 lines) has no domain home:** ~30 private check functions (`validate_cmd.py:23-772`) form a full task-validation engine with no `codeprobe.validation` package, locked behind the Click command — reusable by CI/api/mining self-check if extracted. (Folds naturally into the finding-7 CLI-thinning effort.)

## Leave unchanged (scoped-out, judged healthy)

- **The three-Protocol adapter model** (`AgentAdapter`/`SessionCollector`/`TelemetryCollector`) — a deliberate, documented converge result; finding 5 tightens it, does not replace it.
- **The scorer-honesty lint gate** (`tests/lint/test_scorer_honesty.py`) and the `_KNOWN_OFFENDERS` allowlist discipline — a strong, self-cleaning invariant guard; protect it.
- **The LikeC4 architecture-as-code model** (`architecture/*.c4`) with delivery-state tags — genuinely kept close to source; it is the map, keep it.
- **The `contrib/` research library** — correctly isolated off the CLI (`#research`-tagged), imported by nothing in the core tree; the boundary is clean.
- **`snapshot_cmd.py`** — the correct thin-CLI counter-example that findings 7 and the minor items point *toward*, not away from.
- **The judge/subject LLM split** (adapters vs `core/llm.py`) — principled; only the judge-vs-registry drift (finding 4) needs attention.
