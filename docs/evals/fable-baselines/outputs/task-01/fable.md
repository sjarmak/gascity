## Top 5 I would start today

**1. #3862 — hook projection dedup (P1).**
First step: find the projection site — grep the session config reconciler for the ubs PreToolUse hook write into `.claude/settings.json` — and read the append path. Blast radius: the reconciler's settings-write path and every managed session's settings file; the fix is an idempotent upsert plus a one-time dedup of accumulated entries. Proving test: reconcile twice against a settings.json that already contains the hook and assert exactly one entry; second test starts from N identical entries and asserts collapse to one. What could make this wrong: the append might be intentional for some per-worktree variant I can't see in the issue, and a 5-day-old P1 with this much evidence may already have a maintainer fix in flight — check open PRs before writing code.

**2. #3944 — cook --attach rig context.**
First step: read `decorateFormulaCookGraphV2Recipe` (`cmd/gc/cmd_formula.go:888`) side-by-side with the sling path that passes a real `routedTo`, then thread the invocation's rig context through the cook path. Blast radius: formula cook only; sling untouched. Proving test: two-rig fixture with the same bare agent name in both — cook-with-attach from rig A resolves to A's target; regression test that city-unique names still resolve and that cook outside any rig has defined behavior. What could make this wrong: cook may be deliberately rig-agnostic (it can run outside a rig), so the fix needs an explicit fallback for empty rig context rather than assuming one exists.

**3. #3986 — v2 sling source-bead stamping.**
First step: diff the legacy `--on` branch against the v2 graph branch in the sling command to find where `gc.source_bead_id` is stamped, and add the stamp to the v2 workflow root. Blast radius: the sling v2 attach path; `closeSourceBeadChain` is a read-only consumer that starts working once the metadata exists. Proving test: integration test that slings a bead onto a v2 formula, asserts the root carries `gc.source_bead_id`, and asserts finalize closes the source bead (the `stop reason=no_source` trace disappears). What could make this wrong: v2 might intend a different source-close mechanism (convoy linkage rather than metadata) — verify what workflow-finalize actually reads before assuming parity is the design; and this touches the same decorate plumbing as #3944, so doing both without coordination risks conflicting patches.

**4. #3947 — cron zero-lastRun bootstrap.**
First step: read `checkCron`'s catch-up scan from #2721 and the guard that skips it when lastRun is zero; decide the bootstrap baseline (install/enable time). Blast radius: the order scheduler tick for all cron orders — the danger is making every fresh install "catch up" across an unbounded past window, so the baseline must be creation time, not epoch. Proving test: never-run order whose window has elapsed since install fires exactly once; fresh order whose window has not yet elapsed does not fire. What could make this wrong: the zero-lastRun skip may be a deliberate fire-on-install guard, in which case the correct fix is stamping lastRun at install instead — the same test pins either implementation. #2721's author may regard this residual as theirs; the kind/bug + p2 triage suggests it is open for grabs, but that is inference from labels only.

**5. #3962 — gc init PATH lookup for Gemini.**
First step: grep the provider readiness preflight for the Gemini install check and add an `exec.LookPath("gemini")` fallback (or make PATH primary). Blast radius: init preflight; check whether the discovery helper is shared with the claude/codex checks and fix it once if so. Proving test: preflight passes with a fake `gemini` binary on PATH in a temp dir, fails with the same clear error when absent. What could make this wrong: the hardcoded npm-path check may double as an install-method/version validation (the claude CLI's installMethod banner in #3877 hints such checks exist) — keep any version probe, change only binary discovery.

Ordering rationale: 1–3 are confirmed bugs with the mechanism already pinned to code, where the issue quality does most of the investigation for me; 4 is triaged and precise but carries one semantic decision; 5 is the smallest and safest but also the lowest value, included because it is a guaranteed same-day merge-quality PR. The strongest counterargument to this whole list: everything here assumes no in-flight maintainer PRs, which the snapshot cannot show — the real first action on each pick is a duplicate/PR sweep.
