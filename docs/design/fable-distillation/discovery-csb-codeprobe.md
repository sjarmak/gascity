## 1. Project shape — and the one-vs-two-library decision

**This is two projects that share a discipline, not one project in two repos. They warrant TWO separate skill libraries, with cross-references — not a merged one.** They share no code, no task model, no runner, and no release channel. What they share is a measurement philosophy (contamination-proof tasks, honest scoring, Sourcegraph MCP as the showcase capability). The right structure is a `csb-*` set and a `codeprobe-*` set that cross-link on the shared discipline, exactly as both already cross-link to EnterpriseBench in their own docs.

The two are also **asymmetric in how much new authoring they need**, and this drives the taxonomy in §7:

- **CSB is largely SUPERSEDED by EnterpriseBench.** EB is the evolution of CSB — the 275-task corpus, the dual-verifier idea, the `csb_sdlc_*`/`csb_org_*` families, and the 178 sg-eval mirrors all originate here and were carried forward into EB. Almost every CSB concept is an earlier form of an EB concept the `eb-*` skills already cover. CSB's genuinely-unique, would-die-with-the-fellow surface is small: (a) the **live public-release pipeline** (the `sourcegraph/CodeScaleBench` drop machinery, still operational and carrying an unresolved PII landmine), (b) the **Agent Reliability Observatory** diagnostic layer, and (c) the **migration_eval** 4-tier research sub-project. So CSB's share of the library is intentionally small: ~3 skills, weighted toward lineage and the unique live surface.
- **codeprobe is a LIVE, distinct product**, not superseded by anything. It is a general-purpose measurement _harness_ (`assess → mine → validate → run → interpret`) that mines contamination-proof eval tasks from any repo's history, runs agents (Claude Code / Copilot / Codex) against them, and interprets which config wins. It has its own PyPI release train, 221 test files, a `--cov-fail-under=80` gate, and active dual-verify work on HEAD. It needs the larger share (~10 skills) — but note codeprobe **already has 20 domain skills** covering the operational CLI surface; the gap is the retiring-fellow _doctrine_ layer (integrity doctrine, failure-archaeology, architecture-contract, the hardest-problem campaign), not per-command runbooks.

**CSB task model** (`benchmarks/tasks/<suite>/<task-id>/`): `task.toml` (`[task]` id/repo/`pre_fix_rev`, `[verification] reward_type` e.g. `test_ratio`, `[environment]` resources + inline MCP setup), dual prompts `instruction.md` + `instruction_mcp.md` (baseline vs MCP-armed arm), `tests/` with `ground_truth.json` (files+symbols checklist), `ground_truth_meta.json` (confidence low/medium/high, `ground_truth_source: curator_agent`), `test.sh`, `answer_json_verifier_lib.sh`, `promoted_verifier.py`. The `csb` CLI (`./csb` → `lib/csb/cli.py`, run as `python3 csb`, NOT pip-installed): `run, coverage, postrun, validate, eval, estimate, report, diagnose`.

## 2. Build / test / CI reality (per repo)

**CSB — the CI gate is NOT pytest.** No workflow runs the test suite. `.github/workflows/` gates are: `lint.yml` (`ruff check .`, pinned ruff 0.15.8), `repo_health.yml` (`scripts/maintenance/repo_health.py` + agent-nav freshness check), `docs-consistency.yml`, `eval_kit_standalone.yml` (builds `Dockerfile.eval`, runs `csb eval` in a `--network none` container with no creds — guards the "eval kit has no external deps" promise), `task_smoke_matrix.yml` (task-contract audit + `validate_tasks_preflight.py`), `roam.yml`. Verified traps for a newcomer:

1. **No packaging.** `pyproject.toml` is ruff-config only (no `[project]`, no build-system); this is a script repo. Tests do `from lib.csb...` with **no conftest/pytest.ini/`src` layout** → bare `pytest tests/x.py` gives `ModuleNotFoundError: No module named 'lib'`. Works only from repo root with `PYTHONPATH=. pytest ...` (verified: collects 14 tests in `test_csb_score.py`).
2. **Path-drift.** The committed `Makefile` and several workflow `run:` lines reference flat `scripts/repo_health.py` etc., but those files live at `scripts/maintenance/*.py`. AGENTS.md is correct (`scripts/maintenance/...`); the Makefile targets are stale. The pre-commit gate humans actually run is `python3 scripts/maintenance/repo_health.py [--quick]`.
3. Shell has an `rtk` wrapper intercepting `find`/`pytest` (rejects compound `find` predicates; can print "No tests collected" spuriously).

**codeprobe — CI is strict and multi-gate.** `.github/workflows/ci.yml` (pinned `ubuntu-22.04`, py 3.11/3.12/3.13): `pip install -e ".[dev]"` → `ruff check src/ tests/ scripts/` → `mypy src/codeprobe --strict-optional` → `pytest tests/ -x --cov=src/codeprobe --cov-fail-under=80` → **`python3 scripts/lint_zfc.py` (blocking**, allowlist at `scripts/lint_zfc.allowlist.toml`). Plus `ci-latest.yml` (looser) and `publish.yml` (PyPI via twine, secret `CODEPROBE`). The distinctive gate is `tests/lint/test_scorer_honesty.py` — a lint enforcing `missing-scorer-family`, `quiet-recall-fallback`, `hardcoded-threshold`, `bare-except`. `uv.lock` is committed (289 KB, a premortem mitigation) but CI installs via pip, not uv. Traps: (1) the checked-in `.venv/bin/codeprobe --version` reports a **stale 0.7.1** while pyproject is 0.11.0 — do not trust `--version` as ground truth; (2) `--cov-fail-under=80` is a hard floor; (3) bead-close requires 3 evidence metadata fields + `scripts/check_bead_reachability.py` or the city reopens the bead.
